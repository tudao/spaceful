Credit System Reform (migrations 007)

Decision 10x credit scaling, not a separate companion counter

All credits scaled by 10x (generation 3→30, companion 0.1→1, signup gift 3→30). Daily login grant (10 credits) goes directly into the main profiles.credit_balance — no separate companion daily counter. Keeps the credit system single and legible to users.

Why: A separate counter for companion messages (as originally spec'd in T3) would mean two different credit systems the user has to understand. Single balance wins on UX simplicity.

Decision Daily login grant triggers on app layout load, not a cron

The daily credit grant fires in src/app/(app)/layout.tsx on the first authenticated page load of the day, checked via profiles.last_daily_credit_at. No cron required.

Tradeoff: A cron would be more consistent across all users (even those who don't log in). But for a ritual-first product, we want the reward tied to showing up. Only active users get daily credits. This aligns incentives.

Deviation Signup gift credit amount reads from platform_settings at trigger time

The handle_new_user() Postgres trigger was updated to read signup_gift_credits from platform_settings at the moment of user creation. If platform_settings doesn't exist yet (e.g. during migration), defaults to 30.

Risk: If the trigger fires before migration 007 is applied (during a partial deploy), it falls back to 30 via the coalesce default. Safe.

Open question Renewal credits = signup gift amount?

Subscription renewal currently grants settings.signup_gift_credits (30 credits). This may not be the right amount — monthly renewal could reasonably grant more or less depending on the subscription tier. Not yet wired to Stripe price metadata.

To resolve: When Stripe products are set up, pass credit amount in invoice.metadata.credits (same pattern as checkout.session.metadata.credits).

Stripe Webhook (T1)

Decision Idempotency via note column LIKE match, not a dedicated field

Before granting credits, we check credit_transactions.note LIKE '%{session_id}%'. This avoids adding a new column while still being safe against Stripe retries.

Tradeoff: A dedicated stripe_event_id column on credit_transactions would be cleaner, but the note LIKE approach works given the existing schema and avoids another migration.

Deviation stripe_customer_id not yet on profiles schema

The Stripe webhook looks up users via profiles.stripe_customer_id for subscription events, but this column is not in the current migrations. The webhook will silently skip those events until the column is added.

To fix: Add alter table profiles add column if not exists stripe_customer_id text; to migration 007 or a follow-up. Also update the checkout flow to write stripe_customer_id on session completion.

Companion Memory (T2)

Decision Extraction runs as fire-and-forget after stream closes

The fact extraction Haiku call runs after the SSE stream is fully closed — the user never waits for it. This means the companion context won't include facts from the very message that triggered extraction until the next session.

Tradeoff: Extracting mid-stream would block the response. The one-session lag is acceptable — the companion is building a long-term memory, not real-time state.

Tradeoff String prefix deduplication (first 15 chars) vs semantic similarity

Facts are deduplicated by comparing the first 15 characters of new vs existing facts. This is cheap but blunt — "running 3x/week" and "runs three times a week" would both be stored. Semantic deduplication (embeddings) was considered and rejected as premature before the feature is validated.

Open question companion_context column missing from types.ts

Migration 008 adds companion_context to the spaces table, but src/lib/supabase/types.ts is not regenerated here. Run pnpm db:types after applying migrations to get typed access. Currently cast via as any in the companion chat route.

Activation Sequence Cron (T5)

Deviation array_append via supabase.raw() — not supported in JS client

The activation cron uses svc.raw('array_append(...)') to append the day number to onboarding_emails_sent[]. The Supabase JS client does not support raw SQL in update expressions. This will fail silently at runtime.

Fix needed: Either (a) read the current array, append in JS, write back; or (b) add a Postgres RPC append_onboarding_day(p_space_id uuid, p_day int). Option (a) is simpler but has a race condition. Option (b) is safe. Recommend adding the RPC in a follow-up migration.

Domain Templates (T7)

Decision Domain templates use existing spec resolution, not new DB rows

The 4 domain templates (Founder, Athlete, Student, Creative) are added to the in-memory TEMPLATES catalog in templateCatalog.ts. They do NOT have corresponding space_templates DB rows yet — they rely on the resolveSpec fallback that generates a spec from the template ID.

Consequence: Domain template specs are generated by AI at generation time (same as other templates). If more specific section lists are needed, add DB rows via seed. Template images at /templates/{id}-anime.jpg don't exist yet — the template picker will show a broken image. Add placeholder images before launch.

Decision Domain templates excluded from pickTemplate() auto-selection

The pickTemplate() function filters out templates with a domain field. Domain templates are opt-in only (chosen explicitly in onboarding or settings). This prevents AI from auto-assigning a "Founder" template to someone who just chose "bold" vibes.

Weekly Synthesis Cron (T6)

Deviation Subquery filter uses raw SQL string interpolation

The weekly synthesis cron filters spaces using .filter('id', 'in', '(SELECT ...)') with a raw SQL string. This works with PostgREST but is not type-safe and the date parameter is interpolated directly. Not a SQL injection risk (it's a server-only cron with a static date string), but brittle.

Better approach: Use a Postgres RPC or a two-step query (fetch qualifying space_ids first, then filter). Acceptable at current scale.

Admin Settings Page (T3)

Open question NEXT_PUBLIC_ADMIN_SECRET is client-exposed

The admin settings page uses process.env.NEXT_PUBLIC_ADMIN_SECRET to authenticate API calls from the browser. This secret is visible in the browser bundle. It's only a problem if the secret is the same as your production admin secret.

Recommended fix: Move admin settings behind Supabase RLS checking a is_admin flag on profiles, and use the user's session cookie for auth instead of a shared secret.
